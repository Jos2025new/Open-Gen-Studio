# Reproducciones de sospechas (2026-10-29)

Rama `task/repro-bugs`. Cada sospecha tiene un test que afirma el comportamiento correcto; `it.fails` = bug confirmado (la suite sigue verde y el bug queda registrado). Sin `src/` tocado, sin proveedores reales ni app arrancada. Un fallo por una causa distinta a la anotada se descartó ejecutando cada test como `it` normal.

## 1. Nodes: una conexión entrega otra imagen — CONFIRMADO (4 vías); corregido en 91ea576

Fuente: `docs/rastreo/nodes.md` 3.5 y 3.6. Fixture: nodo «Face» con 3 resultados a1..a3, cable fijo al resultado 3 hacia «Smile».

| Vía | Causa | Test (`tests/repro-nodes-image.test.ts` salvo indicación) |
| --- | --- | --- |
| Borrar resultado 1 de 3: el cable al resultado 3 queda sin salida (`[]`, «no output») | `engine/actions.ts:556` filtra `assetIds` sin reubicar `edge.outputIndex` | `deleting result 1 of 3 leaves the link on the same image (a3)` |
| Borrar resultado 1: un cable al resultado 2 pasa en silencio a a3 (imagen equivocada) | igual | `deleting result 1 leaves a link fixed on a2 delivering a2, not a3` |
| Borrar resultado 1: la elección del nodo (a2) pasa a a3 | igual | `deleting result 1 keeps the node pick on a2` |
| Duplicar el nodo destino: la copia recibe a1, no a3 | `flow/actions.ts:151` reconecta sin `sourceHandle`; `graph.ts:143` pierde `outputIndex` | `a duplicated node keeps receiving a3 from the fixed link` |
| Copiar/pegar el destino: la copia recibe a1 | `flow/arrange.ts:172` igual | `a pasted node keeps receiving a3 from the fixed link` |
| Soltar un cable desde «2» en el fondo: el resultado no recuerda el puerto | `connectionDrop.ts:13` devuelve solo `{x,y,from}`; `addConnected.ts:38-40` no admite puerto | `tests/repro-nodes-drop.test.ts`: `the drop result still carries the port the cable left from` |

Límite: el test de soltar comprueba solo que el puerto no se pierde en `connectionDrop`; el efecto final en `addConnected` sigue por lectura. Control que pasa: `baseline: the link to Smile delivers a3`.

## 2. Nodes: modelo estimado distinto del ejecutado — CONFIRMADO; corregido en ea47987 (con `_modelRef` manda ese modelo)

Fuente: `docs/nodes-controles/hallazgos.md` H2, `docs/rastreo/nodes.md` 5.1. Una operación `relight` (motor `edit`) sobre un asset hecho con nano-banana-2 y `params._modelRef` = seedream: la estimación (`executor.ts:87`) usa seedream; lo que se prepara para ejecutar (`flow/actions.ts:224-228` `nodeChoice` desde el asset de origen, preferido en `jobs.ts:1074`) usa `nano-banana-2/edit`. Test: `tests/repro-nodes-model.test.ts` `the model priced for a relight with _modelRef is the model the run is prepared with` (`it.fails`). El test no decide cuál modelo es el correcto (ADR 0009 dice el confirmado), solo que estimación y ejecución coincidan. El precio mostrado no es el del modelo que corre.

## 3. Límite de gasto con precio desconocido — CONFIRMADO; corregido en e978427 (decidido: pide la confirmación de sobrepasar el límite)

Fuente: `budget.ts:25-27`, `studio-controles/hallazgos.md` H4/H5. Con límite activo ya agotado (gastado 5 de 5, sin aceptar), `overLimit` y `budgetProblem` devuelven «sin problema» para `usd: null`, y `runNodes` (`flow/actions.ts:329`) lanza la ejecución sin ningún aviso. Tests (`tests/repro-spend-unknown.test.ts`): `the gate does not report all-clear...` y `a Nodes run with an unpriced model does not start silently...` (ambos `it.fails`); el control con precio conocido pasa. Los tests no deciden si debe preguntar, bloquear o avisar «el límite no se puede comprobar»: solo exigen alguna señal. Matiz: en el Composer un precio no publicado ya pide confirmación (`Composer.tsx:204`), pero esa confirmación no menciona el límite.

## 4. Pérdida de trabajo en tarjetas

- **H10 CONFIRMADO; corregido en 4403f32** (`tests/repro-cards-typing.test.ts`): escribir con una tarjeta de preguntas abierta envía `User answers (typed): - Who?: (no answer)`, aunque la tarjeta mostraba la opción recomendada. Causa `conversation.ts:51-54` (solo `{note}`) y `:183`. La variante «opción que el usuario pulsó» vivía solo en el estado React de `QuestionsCard.tsx`: reproducida y corregida después (auditoría GPT 2026-10-29) con `agent.cardPick`, que la tarjeta publica en cada cambio (`tests/questions-typed-choice.test.ts`: elegir B, escribir, se envía B).
- **H9 CONFIRMADO; corregido en 1de23c1** (Check status solo cuenta los pasos nuevos) (`tests/repro-cards-recovery.test.ts`): con el límite agotado, «Check status» no ejecuta nada y no ofrece continuar (callejón sin salida). Causa `RecoveryActions.tsx:23-30` (solo `retry` acepta el límite) y `planRun.ts:388`. Por decidir: si Check status debe estar sujeto al límite; el test exige solo «no es un callejón».
- **H11 DESCARTADO como bug**: cerrar la tarjeta de ajustes como `skipped` al escribir es el diseño probado («typing never confirms it», `conversation.ts`, A28); no se escribió test.

Estado 2026-10-29: los `it.fails` de los casos 1 a 4 son ahora `it`. `tests/spending.test.ts` codificaba la regla anterior (precio desconocido no cuenta) y se actualizó a la decisión.
